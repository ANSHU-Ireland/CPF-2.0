# ADR-0001 — Modular monolith, not microservices

Status: Accepted · Date: 2026-07-25 · Owner: Engineering

## Context
Greenfield build; small team; product risk concentrated in domain correctness,
compliance guardrails, and reviewer UX — not in horizontal scale. Assessment
traffic is low-QPS/high-value. The directive requires future separability.

## Options
1. Microservices per module — rejected: operational overhead, distributed
   transactions for session/review consistency, no organisational driver.
2. Serverless functions — rejected: cold starts for session workspaces,
   fragmented audit and tenancy enforcement.
3. **Modular monolith with pure domain package (chosen).**

## Decision
One deployable API (`apps/api`) composed of bounded modules; domain logic in
`packages/assessment-framework` (pure, I/O-free); PostgreSQL as the single
source of truth. Module boundaries follow the directive's list (identity,
tenancy, assessment, review, evidence, data-rights, audit, billing…).

## Separation path
Modules communicate through explicit interfaces and share the DB via
module-owned schemas/tables. First extraction candidates if scale demands:
evidence ingestion (write-heavy) and notifications. Contract = the OpenAPI
spec + event payload schemas, so extraction does not require a rewrite.

## Consequences
+ One deploy, one audit chain, transactional guardrails, fast iteration.
− Requires discipline on module boundaries (enforced in review + lint rules later).

Reversal trigger: sustained >5× projected load on a single module, or a
separate team owning a module end-to-end.

# ADR-0002 — Stack: TypeScript strict + Fastify + zod + PostgreSQL + plain-SQL migrations

Status: Accepted · Date: 2026-07-25

## Decision
Node 22 LTS, TypeScript strict (`noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`), Fastify 5, zod at all boundaries, PostgreSQL 16,
hand-written SQL migrations, npm workspaces, vitest.

## Reasoning
- Boring, mature, hireable, EU-hostable anywhere; no vendor lock-in.
- Fastify: fast, schema-friendly, tiny surface; no framework magic to audit.
- Plain SQL migrations: reviewable by security/compliance, expressive enough
  for RLS/triggers/constraints that an ORM would obscure. An ORM/query builder
  may be added later for app queries (candidate: Drizzle) without changing
  migration strategy.
- vitest 4: fast, ESM-native (v2 pulled vulnerable transitive esbuild — audited
  and upgraded on day one).

## Rejected
NestJS (decorator/DI weight without payoff at this size), Prisma-first schema
(legacy lesson: business constraints ended up outside the DB), Next.js API
routes as backend (legacy lesson: domain logic scattered through UI tree).

# ADR-0003 — Tenancy: shared database, PostgreSQL row-level security, deny-by-default

Status: Accepted · Date: 2026-07-25

## Decision
Every tenant table carries `organisation_id`; RLS policies compare against
`current_org_id()` derived from `app.current_org_id` (SET LOCAL per
transaction by the API). Missing context ⇒ NULL ⇒ no rows. App layer filters
too — RLS is the backstop, and CI verifies RLS is enabled on all tenant tables.

## Options rejected
DB-per-tenant (operational cost at target scale; migration fan-out),
schema-per-tenant (same, milder), app-layer-only filtering (single bug = leak;
legacy had no backstop).

## Consequences
+ One migration path; provable isolation; cheap tenants.
− Careful connection handling (SET LOCAL inside transaction); platform-level
operations need an explicit bypass role with break-glass logging.
Escalation path: dedicated database for regulated/enterprise tenants —
supported because all queries are already org-scoped.

# ADR-0004 — The assessment framework is versioned data; two dimension sets are layered instruments

Status: Accepted (validate with co-founder) · Date: 2026-07-25

## Context
Workbook defines a 10-dimension weighted scoring model; the co-founder
document defines a 7-dimension AI Collaboration Profile with evidence bands.

## Decision
1. Templates, dimensions, anchors, controls, and bands are **immutable
   versioned data** (`frameworkVersion`, SHA-256 checksums, frozen
   `assessment_template_versions`) — sessions bind to a version forever.
2. The 10-dimension model is the **reviewer scoring instrument** (v0.1.0,
   implemented). The 7-dimension profile is the **employer-facing narrative
   lens** assembled by the reviewer from Evidence Ledger claims (Phase 2
   rendering). Integrity context is separate in both.

## Consequences
+ Cohort freeze rule satisfied; instruments can evolve independently; no
  arithmetic ever leaks to employers as a "score".
− Reviewers map claims to profile dimensions — needs good UX + calibration.

# ADR-0005 — AI gateway: provider-independent, disabled by default, kill-switchable

Status: Accepted (design) · Date: 2026-07-25

## Decision
All model calls go through one internal gateway module with: provider adapters,
model + version allow-list and pinning, per-use-case config and prompt
versions, EU data-region routing, token/cost budgets, timeout + bounded
retries, structured-output validation, PII redaction before egress, full
`model_invocations` logging (provider, model, versions, tokens, cost, latency,
region, retention mode), sampling into evaluation sets, org- and platform-level
kill switches. No AI provider is configured in Phase 1; the platform is fully
functional human-only.

## Rule
No AI feature ships unless its AI-governance register entry and evaluation plan
exist (docs/ai-governance). Reviewer-assist output is suggestion-only and its
use/modification is recorded in the oversight record.

# ADR-0006 — Audit log: hash-chained, append-only, in-database

Status: Accepted · Date: 2026-07-25

## Decision
`audit_log` with `prev_hash`/`entry_hash` (SHA-256 over canonical entry +
previous hash), append-only enforced by trigger; chain verification job +
periodic external anchor (Phase 3). In-DB (not external ledger) because the
threat model is tamper-evidence for accountability, not Byzantine trust.

Material events: disclosure acknowledgements, session transitions, scoring
finalisation, report access, permission changes, exports, DSR actions,
retention runs, admin changes, AI invocations (reference).
